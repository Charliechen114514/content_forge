# 文风校准语料

这里保存作者声音与审稿问题。`COMPARE.md` 是作者亲手改稿留下的完整工作坊，里面同时保留坏稿、问题、好稿、逐句修改与 Tips，不能再把它抽薄成几条规则。

- `VOICE.md`：写手开工卡，故意很短；
- `approved.toml`：只收作者逐字原句，供写手校准声音；
- `COMPARE.md`：作者完整改稿工作坊，原样保存前后对照、问题与 Tips；
- `annotations.toml`：正样本的分析与事实边界，只供审稿员；
- `rejected.toml`：坏段落及原因，只供审稿员；
- 整篇文章不会因为进入候选目录就自动成为正样本。只挑经过人工确认的片段。

写手动笔前完整读取 `VOICE.md` 与 `COMPARE.md`，再从 `approved.toml` 取一到两个同场景片段。`COMPARE.md` 不能节选、摘要或改写后再转交：作者的偏好恰恰藏在逐句修改、犹豫、重复和 Tips 里。读取时严格区分其中的标签：`Good`、`好的`、`我会写`、`我的版本` 与 Tips 用于正向校准；“不好的样例”、被引用的原句和“问题”用于识别失败方式，不能当成可模仿句法。

当前声音门禁以 `COMPARE.md` 顶部 Tips 和映射表为准，不再维护一份容易过期的数量摘要。硬禁词、压缩说法、段落人称与无呼吸长句只要命中，全部退回；Reviewer 还必须带上作者确认过的改写方向，不能只报词。字符扫描只能负责兜底，若人称只是「咱们的某某」一类所有格装饰，声音走查仍须判定失败。真正的补充优先用 `>` 块引用分层，但不能把主线必须解释的内容藏进去。

这个完整工作坊是一个经过作者确认的例外。除此之外，初稿前仍然**不要给写手看 `rejected.toml`、`annotations.toml` 或完整审稿规约**。也不要把 `COMPARE.md` 里的 Cinux 事实移植到其他项目；它校准的是写作动作，目标项目的源码和材料才决定事实。

审稿员不参与起草。技术保真审稿读取 `writing_style.md`、`annotations.toml` 与 `rejected.toml`；声音走查完整读取 `COMPARE.md`，检查成稿有没有再次落回工作坊已经指出的问题。两者都只提交问题，不把自己的示范段落覆盖回正文。

新增样本时至少填写：

- `scene`：`opening`、`personal_history`、`concept_entry`、`mechanism`、`transition`、`code_explanation`、`ending` 之一；
- `source` 与 `lines`：能回到上下文复核；
- `provenance = "author_verbatim"`：确认 `text` 是作者逐字稿，而非 AI 润色版；
- `approval = "voice_only"`：可选，表示只能学习声音，技术事实仍待核对。

风格分析、禁仿提醒和事实备注写进 `annotations.toml`，不能和作者原句混放。AI 改过一个字的段落不再声称 `author_verbatim`；要么恢复作者原句，要么不进入正样本。

`COMPARE.md` 不受上面这条 TOML 逐条溯源约束：它不是纯正样本表，而是作者确认过的完整改稿现场，也是这套工作坊目前唯一的正式副本。新增内容直接写进这里，不能另造一份摘要，更不能只留下其中看起来最整齐的几段。文件开头的总 Tips 负责先校准方向，逐案例 Tips 仍然贴着上下文保存。

语料不参与机械 lint。作者原句决定声音，源码与实验决定事实，`writing_style.md` 只供成稿后的审查使用。

编号和结构对称不是天然问题。若内容确实由几条可独立验证的规则、严格步骤或查阅项组成，而且每项紧跟演算或证据，编号就在承担工作。只有“先报数量—贴标签陈列普通论点—末尾复述”的外壳才属于反例。

突然出现的补记要先分层：回答主线遗留问题的内容接回正文；删掉也不妨碍理解的内容才降成块引用或括注；真正会自然产生的疑问可以用口语设问接住。`>`、引言和“有没有朋友注意到”都是阅读层级与语气工具，不是检测到断裂后随机投放的 humanize 外壳。
