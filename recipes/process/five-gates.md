管辖声明:管稿件从「写完了」走到「可以交给人」的流程:何时触发哪道走查、平衡句式与抽象动宾两套主控二审的模板、修订与接缝复查、READY 门禁与留痕。正文自 REVIEW_WORKFLOW.md 五道关一节起整段搬运。

## 五道关

### 0. Intake：当场冻结本次依据

记下赛道、任务模式、源稿与当前成稿的 SHA-256。这不是「交接快照」，而是一张验收单：审稿员到底看的是哪一版，不能靠记忆。

```bash
./scripts/workchop review init <target> --lane <lane> --mode editorial --source <source.md>
```

`target` 可以是含 `article.md` 的发文包，也可以是任意项目的单个 Markdown 草稿。发文包的记录放在包内 `review/`，单文件的记录集中放在本机暂存区（`$CONTENT_FORGE_REVIEW_HOME`，默认 `/tmp/content_forge_review/`），按文章绝对路径隔离，不在目标项目里拉出任何目录。原创草稿没有独立上游源稿时，不传 `--source`。`--lane` 可以填写目标项目自己的稳定名称，不限于平台内置赛道。

### 1. Draft：写手只负责成稿

- 任意项目的技术文章使用 `.claude/agents/content-writer.md`，写手同时遵守目标项目自己的事实、权限与路径约束，不把一个项目的专名和内部流程带到另一个项目。
- 写手包选了声音卡时，完整读取 `VOICE.md` 与作者改稿工作坊 `corpus/COMPARE.md`，再取少量同场景作者真迹，不得让主控把工作坊摘要成几条规则。本包未选声音卡时，按场景卡与目标项目要求起稿，不读取未携带的作者语料。两种情况都不在起稿时背其他审稿清单。
- 编辑性改写以一个完整文件为最小派发单位。写手读完全文、确认本篇主线和事实锚点，再统一重排与改写，不得把若干孤立段落分发成互不知情的「人性化」任务。完成后从头连续读一遍，不能改完最后一段便交稿。

### 2. Walkthrough：四个视角分开看

**声音走查**在本包选了声音卡时，只回答这篇文读起来是不是作者本人；本包未选声音卡时，只检查表达是否满足场景与本包审稿卡的要求，不宣称像某个作者。两种情况都查信息堆积、句式吸引子、导航式转场、莫名其妙的隐喻和过度收敛；选了声音卡时，另查作者原有的吐槽和停顿是否被洗掉。连续技术解释里作者与对方同时消失，属于阻断项，出现人称却只作所有格装饰，同样不能通过。新增口水话还要检查是否有现场触发、是否帮助承接或消化、说完能否回到当前技术问题。

声音走查还要专项抽取平衡类句式：`不是 X，是/而是 Y`、`不在 X，而在 Y`、`并非 X，而是 Y`、`与其说 X，不如说 Y`、`不仅 X，而且/还/更 Y`。命中不是让走查员当场换词，也不能凭自己觉得“这里合理”便静默放行。每一处必须按下面的格式进入问题单，结论为 `CHANGES_REQUESTED`，交主控二次评审：

```markdown
**平衡句式候选｜主控二审**

> 完整原句，一字不省

- X 与 Y 分别是什么：
- 前文是否真实出现 X，或读者是否极可能误认成 X：
- 去掉 X 后信息是否减少：
- 走查员意见：保留候选 / 重写候选（不能代替主控结论）
```

主控必须逐项判断。决定重写的，交写手处理，决定保留的，在 `resolution.md` 使用 `**主控二审结论**`，再次引用完整原句并写明真实对比或递进依据。正文仍保留候选而缺少这份二审结论时，声音 `PASS` 不能记录。

声音走查还要检查疑似 AI 的「用力动词 + 抽象名词」组合，例如「吞掉语义」「击穿边界」「释放价值」。词组中的每个词单独看都可能成立，不能整片机械封杀，命中以后仍必须升级，不能让审稿员凭顺眼静默放行：

```markdown
**抽象动宾组合候选｜主控二审**

> 完整原句，一字不省

- 动词和宾语分别是什么：
- 动词是否对应可观察、可验证的机制：
- 换成普通动作后是否损失技术信息：
- 走查员意见：保留候选 / 重写候选（不能代替主控结论）
```

主控决定保留时，在 `resolution.md` 使用 `**抽象动宾组合二审结论**`，再次引用完整原句并说明这里究竟发生了什么。`一族`与完整组合`压制噪声`已经由作者明确否决，属于硬禁词，不进入这套裁决流程，直接修改。

**保真走查**只看事实：技术结论、代码、命令、路径、链接、引用和源稿中不能丢的限制。它必须逐项核对否定、范围、条件、可能性和编译/链接/运行阶段，检查扩写有没有发明新的原因或状态。它不能以「更规范」为由改成自己的腔调。

**连续性走查**只看正文对自己结构做出的承诺有没有兑现，判据的家在这一节，不另建第二份。抽边在前、验边在后，逐类核验：

- **前提悬空**：句子以「这条规则」「比完 X」接续，仿佛上文的对话已经发生，正文里却没发生过——读者被空投进对话中段，突然被提醒一件还不知道的事。
- **前向承诺**：「待会儿还有单独的一段」「先把话记在这儿」「下面细说」——承诺的内容后来真的来了吗。
- **回望回调**：「刚才」「前面说过」「还记得」——被指的内容真的在那个位置、真是那个样子吗。
- **次序协议**：「从上往下过一遍」「打头的是」「排第二的是」宣布之后守到底了吗，序数半途退化成「再来看」「还得点名」记松脱。
- **计数声明**：「整整八个」与后文逐项点到的内容对得上吗。
- **跨文指针**：正文链接与「到 X 的时候细讲」——目标存在，且真的讲了被声称的内容。
- **未来指针**：指向尚未写出的篇章，对照项目自己的路线判可辩护性。

每条边判四态：兑现／断链／松脱／不可核验。前提悬空与断链是阻断项，松脱与不可核验进问题单，交主控或作者裁决。信号词（待会儿、等到、细说、先把话记、回头、刚才、前面说过、还记得、打头、排第、再来看、点名、整整、第 N 篇）命中只是抽边手段，不作结论，「感觉不连贯」不能立案，必须指明是哪条边、断在哪。走查输入不止单篇：同系列既有正文与项目路线材料都在范围内，单篇不够验边。

**指代可解性走查**只查读者能不能当场知道一句话指向什么。它不与连续性走查合并：目标存在、承诺也兑现，不代表 `001`、`phase2`、“上一轮”或“那个版本”对普通读者可解。抽取裸编号、短代号、阶段名、批次名、临时简称、含糊回指和只有编号/文件名的链接锚文字，逐项追问：

- 它具体指谁。
- 读者此前是否见过并理解这个名字。
- 不搜索仓库、目录和私下材料，能否立即定位。
- 换成内容描述以后，句子是否明显更清楚。

任一项答不上来便立案。源码符号、命令、路径、寄存器名、协议名和必须精确输入的真实构建目标可以保留，但第一次出现仍要说明用途。链接能点开不是放行理由：锚文字只写 `[001]` 或“这里”，读者点击前依旧不知道目标内容。编号确有检索价值时只能作附属信息，标题或内容描述负责承载语义。

四份报告都只列问题，不直接改 `article.md`。每条至少带：文件位置或原句、上下文、为什么卡顿、失真、断链或不可解、修改方向。没有问题也要写明看过哪些边界，不能只留一句 `PASS`。

报告使用一个最小合同，三个小节缺一不能归档：

```markdown
## 范围

实际读过的章节、相邻段落、代码、链接或证据边界。

## 问题

按位置列出问题。这里没有可以静默忽略的 `WARNING`：只要审稿员识别出问题，结论就是 `CHANGES_REQUESTED`，确实没有问题时，才写明「未发现」及判断依据并给出 `PASS`。规则明确允许上下文裁决时，争议照样进入问题单，由主控或作者处理，作者已经声明“不接受申辩”的硬禁词只能修改，不能登记争议后放行。

## 结论

PASS
```

```bash
./scripts/workchop review record <target> voice PASS --report <voice-report.md>
./scripts/workchop review record <target> fidelity PASS --report <fidelity-report.md>
./scripts/workchop review record <target> continuity PASS --report <continuity-report.md>
./scripts/workchop review record <target> reference PASS --report <reference-report.md>
```

`CHANGES_REQUESTED` 表示报告已产生，但稿件尚不能进入下一关。

### 3. Revision：写手收问题，不是审稿员代写

写手按问题单修改，同时留意别把一个局部问题改成全文的新模板。对报告中的每条问题，在 `review/resolution.md` 写「接受并如何处理」或「不接受及理由」。

平衡句式候选不能直接混进普通问题去重。主控要逐条完成二审：若否定半句只是给后半句垫脚，要求写手删掉骨架、直接讲事实，若前文确实存在被否定的理解，或两半确有不可替代的对比/递进关系，可以保留，但必须按上一节的格式在 `resolution.md` 留下依据。

抽象动宾组合也不能混进普通措辞问题。没有可观察机制的，改回具体动作与结果，确实描述机制的，主控按 `**抽象动宾组合二审结论**` 留下原句和依据。

### 4. Recheck：当场看接缝

修改后不只重读被改的那一句。复查者必须连着它的上一段、下一段一起读，并检查：

- 问题真的消失了，而不是换了一种说法。
- 新句子没有让转场、人称和逻辑接口断掉。
- 改动没有让别处欠正文的承诺落空：待会儿要讲的、前面说过的、数过数目的，都要重验。
- 修改没有带来新的事实错误或遗漏。
- 否定词、限定词与阶段关系没有在改写中丢失或变强。
- 没有重复句、残留标点、断裂拼接和代词误用。
- 没有为了让生硬子句显得口语而补上的「呢」，拿掉语气词仍不通顺，就回到主谓、断句和承接关系重写。
- 整篇文没有被审稿意见拉成更整齐、更干的说明书。

```bash
./scripts/workchop review record <target> recheck PASS --report <recheck-report.md>
```

`recheck` 必须在声音、保真、连续性与指代可解性四项都记录为 `PASS` 之后执行。它会绑定当时的 `article.md` 哈希，之后再改正文，状态会自动变回 `STALE`。

### 5. Ready：机器只判定证据是否齐全

```bash
./scripts/workchop review status <target>
./scripts/workchop review ready <target>
```

`ready` 会校验报告完整性、版本一致性，并强制运行 Humanizer 硬门禁。任一散文段落无人称、人称全部只是所有格装饰，或者命中其他硬规则，都不可能成为 `READY`。它仍然无法独自判断文章是否真的好读，所以声音走查不能省略，报告为空、源稿变化、正文在复查后又变化，同样不能通过。

`mechanical` 模式不生成声音与保真报告，只记一份机械检查结果：

```bash
./scripts/workchop review record <target> mechanical PASS --report <check-report.md>
```

## 日常模式

发文包生成后 STOP，交给用户过目。`READY` 是交付用户前的内部门禁，不代替用户的判断。

## 独立性的底线

- 有子 Agent 时，写手、声音走查、保真走查、连续性走查、指代可解性走查使用独立上下文。走查者只读它需要的材料，不读写手的自辩。
- 没有子 Agent 时，同一模型也要分五轮执行：写完后关闭提纲与生成过程，分别以四份独立清单冷读，再回到写手身份修改。
- “独立”不是多走一次 lint。Lint 只会报模式，看不见术语空降、话题断裂和被洗掉的作者性格。

## 包内留痕

```text
<package-dir>/
├── article.md
├── meta.md
└── review/
    ├── manifest.json
    ├── voice.md
    ├── fidelity.md
    ├── continuity.md
    ├── reference.md
    ├── resolution.md
    └── recheck.md
```

单文件草稿的记录则落在 `$CONTENT_FORGE_REVIEW_HOME/<stem>-<hash>.review/`，内部文件相同。

发文包的这些记录跟着稿件走 Git，是验收证据，单文件的记录是本机工作状态，放在暂存区，重启清空也不动目标项目——需要留档的结论写进对应报告或提交说明。
